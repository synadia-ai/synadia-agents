# `test-fixtures/identity/` — shared sender-identity test fixtures

Repo-level fixtures for the **sender-identity extension** of the Synadia Agent
Protocol. All four SDK test suites —
`client-sdk/typescript`, `agent-sdk/typescript`, `client-sdk/python`,
`agent-sdk/python` — consume the same files, so the TypeScript and Python
SDKs are exercised against byte-identical nats-server topologies.

| File                          | What                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `keys.json`                   | Five throwaway user nkeys (alice, bob, carol, dave, erin): public key + seed text. **Test-only. Never reuse.**                        |
| `agent-id-fixtures.json`      | The spec's agent-ID parse table (first ten rows, in order) plus extra rows: bad-CRC account, empty tokens, unrepresentable names, `new()`. |
| `nkey-noaccounts.conf`        | One nkey user, no accounts (global account `$G`).                                                                                     |
| `nkey-deny-sys.conf`          | One nkey user with `publish: { deny: "$SYS.>" }` — `$SYS.REQ.USER.INFO` becomes a permissions violation.                              |
| `accounts.conf`               | Four config-file accounts: ACME exports `agents.>` / `$SRV.>`; APP (`share: true` + a `to:` rename), APP2 (no `share`), APP3 (rename-only). |
| `account-token-position.conf` | ACME exports `svc.*.prompt` with `account_token_position: 2`; APP imports it both with and without `to:`; APP2 without `share`.        |
| `closed-import.conf`          | ACME denies every local user direct prompt/status publishes; APP reaches the AgentService export through `share: true`, making request-info operator attestation a real deployment precondition rather than a test assertion. |
| `sender-vectors.json`         | Known-answer vectors for the `Agent-Sender` header (generated by the TS SDK, verified by every SDK).                                  |
| `id-sig-vectors.json`         | Known-answer vectors for the `AGENT-ID-V1` registration signature (generated by the TS SDK, verified by every SDK).                   |
| `operator/`                   | The operator-mode (T5) topology: `operator.conf` (operator JWT, `resolver: MEMORY`, preloaded SYS / ACME / APP account JWTs), `alice.creds` / `carol.creds` (ACME), `bob.creds` (APP, imports ACME's `agents.>` and `$SRV.>` with `share: true`), `keys.json`, and the `@nats-io/jwt` generator. See below. |

Rules that keep the four suites honest:

- **Configs are port-less.** The harnesses always pass `-a 127.0.0.1 -p <port>`,
  which supplies the listen address on the command line (verified on
  nats-server 2.12.7) — no templating, no substitution. JetStream is
  `-js -sd <tmpdir>` on the command line for the same reason; there is no
  `jetstream.conf`.
- **Literal keys.** Every `nkey: "U…"` in every `.conf` is one of the
  `keys.json` public keys, verbatim. A unit test in each suite asserts that
  every literal is a `keys.json` user, that each config names exactly the
  users its header comment promises, and that every seed derives its public
  key — regenerate the keys and every config must change with them.
- **Lint:** `for f in test-fixtures/identity/*.conf test-fixtures/identity/operator/*.conf; do nats-server -t -c "$f"; done`
  — also a CI step in each SDK workflow.
- **Test vectors** — `sender-vectors.json` (exact `Agent-Sender` header
  bytes, signed inputs, signatures and framed wire lengths, incl. an empty
  payload, a non-ASCII name, a renamed-import `sub` and unsigned claims) and
  `id-sig-vectors.json` (`AGENT-ID-V1`, incl. a custom prompt subject) are
  **generated by the TypeScript implementation**:
  `cd client-sdk/typescript && bun scripts/generate-identity-vectors.ts`
  (`--check` compares without writing; a unit test asserts the files are
  byte-identical to a regeneration). Every SDK verifies them; only the TS
  generator writes them.
- `.gitignore` ignores `*.creds` / `*.nkey` repo-wide and negates exactly
  `test-fixtures/**/*.creds` and `test-fixtures/**/*.nkey` (not a blanket
  `!test-fixtures/**`, which would un-ignore the `node_modules/` under
  `operator/`).

## Operator-mode fixture (`operator/`, T5)

Everything the config-file topologies cannot show: 113-character agent IDs
whose `account` is the account public NKEY, the credentials-JWT source of
`selfId()`, and a `share: true` import whose `Nats-Request-Info` stamp names
the caller's account by its 56-character key — the NGS shape of the host
SDKs' operator-attested mode.

- `operator.conf` is port-less like the others (`-a/-p` on the command
  line) and lints with `nats-server -t`. Accounts are resolved from memory
  (`resolver_preload`); `system_account` is set so `$SYS.REQ.USER.INFO`
  answers. No user JWT expires.
- Users authenticate with the `.creds` files (`credsAuthenticator` /
  `user_credentials`). ACME (alice, carol) exports `agents.>` and `$SRV.>`
  as services with `response_type: Stream`; APP (bob) imports both with
  `share: true`; SYS has no users.
- **Regenerating** mints new keys — JWTs carry `iat`, so the output is never
  byte-identical, and there is no `--check`:
  `cd test-fixtures/identity/operator && bun install && bun generate.ts`.
  Commit the whole directory together. The generator is the only place in
  the repo that uses `@nats-io/jwt` (a prerelease that pins nkeys 1.x — hence
  its own `package.json`, never a dependency of an SDK). Its account JWTs
  set every limit to `-1` explicitly: without a `limits` block the server
  reads `0` ("more exports than allowed by the operator") and refuses the
  users.
- Same rule as `keys.json`: test-only, never reuse, rotation means new keys.

Consumed by `client-sdk/typescript/test/integration/identity-t5-operator.test.ts`
(the Python suites do not use it yet).

## Regenerating `keys.json`

The keys were minted with `@nats-io/nkeys`:

```ts
import { createUser } from "@nats-io/nkeys";
const kp = createUser();
kp.getPublicKey(); // "U…"  → "public"
new TextDecoder().decode(kp.getSeed()); // "SU…" → "seed"
```

Then replace every occurrence of the old public key in every `.conf` and run
the fixture unit tests in all four suites.

A seed that has been committed cannot be revoked, only abandoned — which is
fine for keys that only ever authenticate to a per-test `nats-server` bound
to `127.0.0.1`, and is exactly why they must never be reused anywhere else.
Rotation therefore means *new* keys: never re-add a pair that was once
removed.
